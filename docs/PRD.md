## 1. 产品定位

**一句话**：一个以大模型 Agent 为主要劳动力的自动化项目管理平台——需求从微信等入口自然语言流入，由产品专家 Agent 拆解成需求单，经管理员确认后进入任务池，分布在不同终端的开发/测试 Agent 自动认领、开发、测试、提交，管理员只在关键节点（需求确认、分支合并、验收）介入。

**核心价值**：
1. **需求零摩擦流入**——客户在微信里说话，系统里就有结构化需求单
2. **开发测试全自动**——任务池驱动，多终端 Agent 并行认领执行
3. **人只做决策**——管理员的工作收敛为三次审批：确认需求、合并分支、验收
4. **全程可追溯**——需求来源 ↔ 需求单 ↔ 分支 ↔ 测试报告 全链路映射

**服务对象**：
- **管理员/项目负责人**（人）：审批、看板、合并、验收，高频使用手机端
- **开发/测试 Agent**（不同终端上的大模型智能体，如 Claude Code、BitSoulClaw 终端）：通过账号密码 + API 接入平台干活
- **客户/需求提出人**（人）：在微信中提需求、接收反馈包

**首批管理的项目**：
1. BitSoulClaw（Electron 桌面应用）
2. bitsoulofficial（官网，Python 后端 + 前端）
3. minsheng-worklog-mp（微信小程序）

后续支持项目级增删改查与权限分配。

## 2. 角色与 Agent 定义

| 角色 | 类型 | 职责 | 运行位置 |
|---|---|---|---|
| 管理员 | 人 | 需求确认、优先级复核、分支审查合并、验收、系统配置 | Web / 手机 H5 |
| 项目负责人 | 人 | 查看看板与日报（MVP 阶段与管理员同权限） | Web / 手机 H5 |
| 产品专家 Agent | 平台内置 LLM Agent | 需求解析、拆分、补全、生成澄清问题、多模态内容理解 | 平台服务端 |
| 项目管理专家 Agent | 平台内置 LLM Agent | 基于池中全量任务做优先级排序与打标、生成每日进度报告 | 平台服务端 |
| 测试专家 Agent | 平台内置 LLM Agent | 依据需求单与开发提交生成测试任务、拆分打标、排优先级 | 平台服务端 |
| 开发 Agent | 外部终端 LLM Agent | 登录平台 → 认领开发任务 → 拉取上下文 → 开发 → 提交分支 | 各开发终端 |
| 测试执行 Agent | 外部终端 LLM Agent | 认领测试任务 → 执行测试 → 输出测试报告 → 提交 | 各测试终端 |
| 微信采集 Bot | OpenClaw 机器人 | 监听指定微信群/好友，转发文本、图片、文件到平台 | OpenClaw 所在终端 |

## 3. 核心业务流程

### 3.1 需求全生命周期状态机

```
[采集箱] → [拆解中] → [待确认] → [待开发] → [开发中] → [待测试]
              ↑            │(驳回/修改)                      │
              └────────────┘                                ↓
[已验收] ← [待验收] ← [审核中] ← [测试完成] ←──── [测试中] ←─┘
                         │(测试不通过 → 回到待开发，生成缺陷任务)
```

状态定义：

| 状态 | 含义 | 触发者 |
|---|---|---|
| 采集箱 inbox | 原始消息已入库，未拆解 | 微信 Bot / 手动导入 |
| 拆解中 parsing | 产品专家 Agent 正在解析拆分 | 系统 |
| 待确认 pending_confirm | 拆分结果等待管理员确认，可编辑/合并/拆开/驳回 | 系统 |
| 待开发 ready | 已确认，进入待开发池，已由项管 Agent 标注优先级 | 管理员确认 |
| 开发中 developing | 已被某开发 Agent 认领，feature 分支已创建 | 开发 Agent 认领 |
| 待测试 pending_test | 开发提交完成，测试专家 Agent 已生成测试任务入测试池 | 开发 Agent 提交 |
| 测试中 testing | 测试任务被测试 Agent 认领执行 | 测试 Agent 认领 |
| 测试完成 tested | 测试报告已提交 | 测试 Agent 提交 |
| 审核中 reviewing | 平台自动审核（报告结论 + 规则校验） | 系统 |
| 待验收 pending_accept | 审核通过，等待管理员/客户验收 | 系统 |
| 已验收 accepted | 管理员点验收，或客户体验包确认 | 管理员 |

补充规则：
- 测试不通过：需求回到「待开发」，自动生成缺陷任务（关联原需求单，优先级默认提一级）
- 任一状态管理员可手动关闭（closed）或挂起（on_hold）
- 认领超时（可配置，默认 4 小时无心跳）自动释放回池

### 3.2 需求流入（多入口）

**入口 A：微信机器人（MVP 主入口）**
- OpenClaw 微信 Bot 监听管理员配置的群/好友白名单
- 支持文本、图片、文件（文档）三类消息；语音消息 MVP 阶段先存档不转写（P2 接 ASR）
- 消息按「会话 + 时间窗」聚合：同一会话 30 分钟内的连续消息合并为一个「需求线索」再送拆解，避免一句话一个需求单（窗口时长可配置）
- 群消息支持指令触发模式（可配置）：默认全量采集进采集箱；也可设置只采集 @机器人 或带 #需求 标记的消息
- 每条需求单永久记录来源：微信会话 ID、发送人、原始消息原文/文件

**入口 B：管理后台手动导入（MVP 兜底）**
- 粘贴聊天记录文本 / 上传截图 / 上传文档，选择所属项目与来源客户，送产品专家 Agent 拆解
- 用于微信通道故障或非微信来源（口头、邮件等）

**入口 C：Web 表单**（P1）——客户或团队成员直接在 H5 页面结构化提交

**入口 D：实时语音需求沟通模块**（P2，详见 §4.8）

### 3.3 需求拆解与确认

1. 产品专家 Agent 对需求线索做：
   - **项目归属判断**（结合来源会话与项目绑定关系，判断不了则标记待管理员指定）
   - **拆分**为一个或多个独立需求单，每单包含：标题、用户故事、验收标准（可测试的条目列表）、涉及模块猜测、预估复杂度（S/M/L）、多模态附件引用
   - **澄清问题清单**：不确定的点列成问题，附在需求单上
2. 管理员在「待确认」列表（手机端优先设计）逐条操作：确认 / 编辑后确认 / 合并多单 / 拆开 / 驳回（驳回可填原因，Agent 重新拆解）
3. 澄清问题可一键生成微信回复文案，由管理员转发给客户；客户回复回流后 Agent 自动补全需求单（P1 自动关联，MVP 手动补充）

### 3.4 优先级排序

- 项目管理专家 Agent 在以下时机对**待开发池全量任务**重排：新需求确认入池、缺陷任务生成、每日凌晨定时、管理员手动触发
- 输出：P0（阻塞/线上缺陷）/ P1（高价值）/ P2（常规）/ P3（低优）+ 排序理由 + 池内相对顺序
- 排序依据：客户来源权重（可按客户配置）、缺陷优先、需求间依赖、复杂度、项目当前吞吐
- 管理员可手动锁定某任务优先级（锁定后 Agent 不再改动）

### 3.5 分支模型与开发流程

```
main ←──(管理员每晚审查合并)── daily/20260803 ←──(自动合并)── feature/REQ-123
```

1. **每日分支**：平台每天凌晨（默认 02:00，可配置）为每个活跃项目从 main 自动创建 `daily/YYYYMMDD` 分支
2. **需求分支**：开发 Agent 认领需求后，平台自动从当日分支创建 `feature/REQ-<id>`，认领响应中告知 Agent 分支名与仓库地址
3. **开发提交**：Agent 在 feature 分支上开发并 push，调用「提交完成」API 时附提交说明与自测结果；平台自动将 feature 分支合并进当日分支（冲突则标记需人工处理并通知管理员）
4. **每晚合并**：管理员在平台「分支审查」页查看当日分支的变更汇总（按需求单分组的 diff 摘要、测试报告结论），确认后一键合并回 main（也可逐需求 cherry-pick / 剔除，P1）
5. **需求 ↔ 分支映射**：需求单详情页永远可见：来源客户/会话 → feature 分支 → 所在 daily 分支 → 是否已进 main → 关联 commit 列表。支持按客户筛选「他的需求都在哪些分支」，用于定向打包反馈体验

### 3.6 测试流程

1. 开发提交后，测试专家 Agent 读取需求单（含验收标准）+ 提交 diff 摘要，生成测试任务：用例列表（步骤/预期）、测试类型标签（功能/回归/边界/兼容）、优先级
2. 测试任务进入测试池，测试 Agent 通过 API 认领（可与开发 Agent 是不同终端；平台强制**同一需求的开发与测试不能被同一 Agent 账号认领**，可配置关闭）
3. 测试 Agent 在当日分支（含该需求代码）上执行测试，输出结构化测试报告：逐用例结果、通过率、缺陷描述、日志/截图附件
4. 报告提交到平台并作为文件提交到当日分支的 `docs/test-reports/` 下；平台依据报告结论自动流转状态

### 3.7 上下文共享与文档自动化

- 平台自动在每个被管理项目仓库的 `docs/` 目录（无则创建）维护：
  - `docs/requirements-log.md`：需求日志（新增/变更/验收，追加式）
  - `docs/dev-log.md`：开发日志（每次需求提交自动追加：需求、分支、变更摘要、Agent）
  - `docs/agent-context.md`：项目级共享上下文（架构要点、约定、当前迭代重点），管理员与产品专家 Agent 共同维护
- 开发/测试 Agent 认领任务时，「拉取上下文」API 返回：需求单全文 + 验收标准 + agent-context 内容 + 相关历史需求摘要，确保各终端智能体信息一致

### 3.8 看板与报告

**看板三层颗粒度**（管理员每晚手机查看为主场景）：
1. **全局看板**：各项目健康度卡片（待确认数、池深、今日完成、阻塞项）、今日 Agent 活跃数、LLM 消耗
2. **项目看板**：需求状态泳道（Kanban）、当日分支状态、燃尽/吞吐趋势、需求来源分布
3. **Agent 看板**：每个 Agent 账号的当前任务、历史完成数、平均耗时、一次通过率（测试通过无返工比例）

**统计指标**（P1 完整版）：需求前置时间（流入→验收）、开发/测试时长分布、返工率、各客户需求量与验收率、LLM token 成本分项目/分 Agent 统计

**每日进度报告**：每晚（默认 21:00）项目管理专家 Agent 按项目生成：今日完成/进行中/受阻、明日预测、风险提示；在平台展示并通过微信 Bot 推送给项目负责人（P1 推送）

### 3.9 打包反馈闭环（P1）

- 需求单验收前，管理员可对某客户的需求集合发起「体验包」：选择分支（feature 或 daily），触发该项目的构建脚本（项目级配置构建命令），产出物挂到需求单
- 通过微信 Bot 将体验包链接/文件发给来源客户，客户反馈回流为新的需求线索并自动关联原需求

场景：开发人员与客户现场对接，录音设备实时推送语音流/文本流。
- 实时 ASR 转写 → 大模型流式提取需求要点、实时拆分

- 全链路延迟目标 < 3s（语音说完到问题提示）

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 移动端 | 所有管理员操作页面（确认、审批、看板、合并）必须手机可用；采用响应式设计，审批类页面以手机优先设计 |
| 可用性 | 单机部署容忍重启；队列任务持久化，进程崩溃不丢消息；微信 Bot 断连自动重连 + 兜底手动导入 |
| 安全 | API Key AES-256-GCM 加密存库；Agent 走独立 token，权限最小化（只能读写自己认领的任务）；平台外网访问走 HTTPS；Git 仓库不对公网匿名开放 |
| 可追溯 | 需求、任务、分支、报告、Agent 操作全部留痕，时间线可回放 |
| LLM 成本 | 每次调用记录 token 用量并归属到项目/需求/Agent 角色；支持设置每日消耗上限告警 |
| 性能 | 平台并发规模小（个位数人 + 十位数 Agent），不做高并发设计，但 LLM 调用一律异步队列化，界面不阻塞 |

## 6. MVP 验收场景（端到端）

> 与需求说明书中的「最小 MVP」逐条对应。

1. 客户在微信群发一段需求（含一张截图）→ 平台采集箱出现需求线索
2. 产品专家 Agent 自动拆解为 2 个需求单（含验收标准与 1 个澄清问题）→ 状态「待确认」
3. 管理员在手机上编辑其中一单并确认 → 两单进入待开发池，项管 Agent 标注 P1/P2
4. 平台当日已自动创建 `daily/20260803` 分支
5. 某终端上的 Claude Code 按接入指引，用 Agent 账号登录 → 认领 P1 需求 → 平台创建 `feature/REQ-1` 并返回上下文 → Agent 开发、push、调用提交 API
6. 平台合并 feature → daily，状态到「待测试」，测试专家 Agent 生成 3 条测试用例任务
7. 另一终端测试 Agent 认领 → 执行 → 提交测试报告（全部通过）→ 报告出现在仓库 `docs/test-reports/`
